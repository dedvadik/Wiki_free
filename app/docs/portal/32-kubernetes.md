Как запустить портал в Kubernetes так, чтобы он переживал падение узлов и сам подстраивался под нагрузку: добавлял копии при росте и отдавал мощность при спаде. Чарт — `kubernetes/helm/wikispace/` в корне репозитория, инструкция по установке — `kubernetes/README.md`.

## Блоки

Каждый блок — отдельный компонент со своими копиями, проверками здоровья и правилами размещения по узлам:

| Блок | Ресурс Kubernetes | Копии | Где работает |
| --- | --- | --- | --- |
| **web** — приложение | Deployment + HPA | 2…20, по нагрузке | по одной на узел и зону (`topologySpreadConstraints`) |
| **pooler-rw** — PgBouncer для записи | CloudNativePG Pooler | 2+ | на разных узлах |
| **pooler-ro** — PgBouncer к репликам | CloudNativePG Pooler | 2+ | на разных узлах |
| **database** — PostgreSQL | CloudNativePG Cluster | 1 основной + реплики | каждый экземпляр на своём узле |
| **storage** — загруженные файлы | PVC ReadWriteMany | общий для всех копий web | хранилище кластера |

Каждому блоку можно назначить свой пул узлов (`nodeSelector`, `tolerations`): например, копии web — на узлы `workload=web`, а PostgreSQL и пулеры — на `workload=db`. Пример — `kubernetes/examples/values-production.yaml`.

## Почему копии web взаимозаменяемы

Приложение не хранит состояния внутри копии, поэтому пользователь может попасть на любую:

- **сессии** лежат в PostgreSQL, а секрет подписи cookie (`SESSION_SECRET`) общий — из Secret чарта;
- **файлы** хранятся на общем томе: видео, загруженное через одну копию, отдаёт любая другая;
- **настройки сайта** кэшируются в памяти каждой копии, но раз в `SETTINGS_SYNC_SECONDS` перечитываются из базы (`startSettingsSync` в `services/settings.js`). Изменение в админке доходит до всех копий за несколько секунд. Это опрос маленькой таблицы, а не LISTEN/NOTIFY: он работает и через PgBouncer в режиме транзакций;
- **версии** `/theme.css` и статики — хеш содержимого, а не время запуска. У всех копий из одного образа они одинаковые, и кэш браузера не сбивается при переходе между копиями;
- **кэш готового HTML статей** привязан к номеру версии страницы, поэтому устаревшее содержимое не отдаёт ни одна копия.

## Запуск копии и подготовка базы

```text
init-контейнер prepare-db (node src/tools/prepare.js)
   │  напрямую к основному PostgreSQL, мимо PgBouncer
   │  миграции        — под advisory-блокировкой (db/migrate.js)
   │  администратор,
   │  демо-контент    — под блокировкой (bootstrapData в services/bootstrap.js)
   │  документация    — под блокировкой (если DOCS_IMPORT=true)
   ▼
основной контейнер (RUN_MIGRATIONS=false) — сразу обслуживает запросы через PgBouncer
```

Блокировки позволяют безопасно стартовать любому числу копий одновременно: работу выполнит первая, остальные за миллисекунды увидят готовую базу. Напрямую, а не через пулер, — потому что advisory-блокировка привязана к соединению, а PgBouncer в режиме транзакций подменяет соединения между запросами. Вспомогательная функция — `withAdvisoryLock` в `db/pool.js`.

## Проверки здоровья и остановка

| Адрес | Проба | Что проверяет |
| --- | --- | --- |
| `/livez` | startup, liveness | процесс жив. **Без обращения к базе**: иначе при сбое PostgreSQL Kubernetes перезапустил бы все копии разом, хотя они сами переподключатся |
| `/healthz` | readiness, Docker HEALTHCHECK | процесс, база и то, что копия не останавливается; 503 — балансировщик не шлёт сюда запросы |

Остановка по `SIGTERM` идёт в два этапа (`server.js`, `services/lifecycle.js`):

1. `/healthz` начинает отвечать 503, копия выходит из балансировки. Ещё `SHUTDOWN_DELAY_SECONDS` она принимает запросы, которые успели к ней направить.
2. Новые соединения закрываются, начатые запросы дорабатываются до `SHUTDOWN_TIMEOUT_SECONDS`, затем закрываются пулы БД.

Поэтому уменьшение числа копий и обновление проходят для пользователей без ошибок. `server.keepAliveTimeout` — 65 с: дольше, чем держит соединения nginx, иначе часть запросов получала бы 502.

## Автомасштабирование

```text
нагрузка ↑ → средний CPU копий > порога → HPA: до ×2 копий за 15 с
           → копиям не хватает места → Pending → автоскейлер кластера добавляет узел
нагрузка ↓ → 5 минут низкой нагрузки → HPA: −1 копия в минуту
           → узел опустел → автоскейлер удаляет узел
```

- **HPA по CPU**, `autoscaling/v2`. Порог — 70% от `requests.cpu` (500m), то есть ~0,35 ядра или ~50 запросов/с на копию. Копия насыщается на ~1 ядре (~145 запросов/с), так что новые добавляются заранее. По памяти масштабирование не включено: Node.js не спешит отдавать память после пика, и HPA не смог бы уменьшить число копий.
- **KEDA** (по желанию) масштабирует ещё и по метрике `wikispace_http_requests_in_flight`: реагирует на всплеск раньше, чем вырастет загрузка CPU.
- **Метрики Prometheus** (`services/metrics.js`) отдаются на отдельном порту `METRICS_PORT`, который наружу не публикуется: запросы по статусам, гистограмма времени ответа, запросы в работе, задержка цикла событий Node.js, соединения пула PostgreSQL, память и CPU.
- **PodDisruptionBudget** не даёт автоскейлеру узлов и плановым работам выселить все копии сразу. Копии web помечены `safe-to-evict`: они не хранят состояния.

## PostgreSQL: реплики и переключение

Кластер CloudNativePG держит основной сервер и реплики на разных узлах. При сбое основного оператор за 10–30 с делает основным самую свежую реплику; приложение переподключается само, а копии web не перезапускаются (liveness не зависит от базы).

**Чтение с реплик.** Если задан `DATABASE_READ_URL`, самые тяжёлые запросы на чтение — поиск и страница меток — идут на реплики через pooler-ro (`readPool` / `readMany` в `db/pool.js`). Реплики отстают на доли секунды, для поиска это незаметно.

**Соединения.** Каждая копия держит до `DB_POOL_MAX` соединений с PgBouncer. Сам PgBouncer держит к PostgreSQL только `defaultPoolSize`, поэтому 20 копий не создают 200 подключений к серверу.

## Проверка

Чарт проверялся в кластере k3s: `helm lint`, строгая проверка манифестов по схемам (kubeconform, включая ресурсы CloudNativePG), затем установка и сценарии под нагрузкой. Подробности — в `kubernetes/README.md`.

| Сценарий | Результат |
| --- | --- |
| две копии одновременно готовят базу | работу сделала одна, вторая дождалась блокировки |
| взаимозаменяемость копий (сессия, файлы, настройки, версии статики) | 12 из 12 проверок |
| рост нагрузки | HPA: 2 → 6 копий за ~40 с, новые копии готовы за ~11 с |
| удаление копии под нагрузкой | замена за ~20 с, ошибок нет |
| два полных обновления всех копий под нагрузкой | 0 ошибок из 38 995 запросов |
| снятие нагрузки | копии плавно убраны до минимума |
| сбой основного PostgreSQL под нагрузкой | реплика стала основным сервером автоматически, приложение восстановилось за ~20 с без перезапусков |

Первый прогон обновления выявил 17 ошибок 502 из 51 781 запроса: прокси повторно использовал keep-alive соединение с останавливающейся копией. Поэтому при остановке копия отвечает с `Connection: close` (middleware в `app.js`).
