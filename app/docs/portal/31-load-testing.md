Сколько людей выдерживает портал, насколько большой может быть база, какие файлы можно загружать и что происходит при перегрузке. На этой странице — результаты нагрузочного тестирования и исправления, которые оно вызвало. Сценарии лежат в `tests/load/`, инструкция по запуску — в `tests/load/README.md`.

## Коротко

:::info Итог на тестовом стенде (ноутбук, 4 ядра)
- **До ~600 активных пользователей одновременно** (каждый что-то открывает раз в 5–15 секунд) — комфортно: половина запросов быстрее 20 мс, 95% — быстрее 0,15 с (в одном из повторов, на фоне нехватки памяти у ноутбука, — 1,2 с), ошибок нет.
- **~1000 активных** — предел для этой машины: работает без ошибок, но задержки то в норме (p95 0,7 с), то вырастают до секунд.
- **2000 пользователей «онлайн»** (заходят раз в 30–60 секунд — обычный режим вики) — комфортно: p95 0,12 с. По пропускной способности потолок таких пользователей — порядка 4–5 тысяч.
- **База**: 20 000 страниц — 270 МБ, 100 000 страниц — 1,36 ГБ (и на ней 600 активных пользователей работают без ошибок, p95 0,38 с). Время открытия одной статьи от размера базы почти не зависит.
- **Файлы**: любые типы до 20 МБ (`UPLOAD_MAX_MB`); в браузере открываются только растровые картинки, остальное скачивается.
- **Перегрузка** не ломает портал: при 1500 активных задержки — десятки секунд, но ошибок 0,01%, а после спада нагрузки всё сразу возвращается к норме.
:::

Если в организации онлайн одновременно 10–20% сотрудников, такого стенда хватает на компанию в несколько тысяч человек. На выделенном сервере цифры будут выше: здесь генератор нагрузки работал на той же машине и отнимал у портала процессор.

Словарь тестовых текстов распределён по закону Ципфа, как живой язык: слово «сервер» есть почти на каждой странице (худший случай для поиска), а редкие термины встречаются на единицах страниц.

:::warning Шум стенда
Ноутбук параллельно выполнял другие программы и работал при нехватке памяти (Windows сжимала память). Поэтому повторные прогоны одного сценария иногда различались, особенно у предела (1000 пользователей). Ниже приведены оба результата там, где они расходились.
:::

## Что нашёл тест и что исправлено

Первый прогон на 20 000 страниц показал **12 запросов в секунду** при пяти читателях и поиск дольше секунды. После исправлений — **122 запроса в секунду** на той же смеси, в 10 раз больше.

| Проблема | Было | Стало |
| --- | --- | --- |
| В боковую панель каждой статьи попадало **всё дерево** пространства | статья в пространстве на 5 000 страниц — 386 мс и 1,6 МБ HTML; страница пространства — 371 мс | 16–22 мс и 30 КБ; 10 мс. Показывается путь к открытой странице, остальные ветки подгружаются при раскрытии |
| Поиск **читал всю таблицу**: условие «индекс ИЛИ подстрока в заголовке» без индекса у второй части | несуществующее слово — 355 мс | 7 мс (триграммный индекс `pg_trgm`) |
| Поиск **ранжировал все совпадения** | слово, которое есть на 20 000 страниц, — 1 250 мс | 110 мс (ранжируются 1 000 самых свежих совпадений) |
| Нет индекса по `parent_id` | каждый показ статьи просматривал таблицу, чтобы найти дочерние | индекс `pages_parent_idx` |
| EJS проверял существование файла на диске при **каждом** `include` | 16% всей работы процессора | 0: переопределения из `custom/views` проверяются один раз |
| Markdown разбирался заново при каждом показе | ~2,5 мс на статью | кэш готового HTML по номеру версии |
| Проверка пароля (bcrypt) **останавливала основной поток** на ~80 мс | 1000 пользователей входят за 1,5 мин: p95 12,3 с, максимум 60 с, 0,6% ошибок | p95 0,98 с, максимум 2,9 с, 0% ошибок — bcrypt в пуле потоков |
| Лимит формы (5 МБ) меньше лимита статьи (2 млн символов) | русская статья длиннее ~0,8 млн символов получала непонятную ошибку 413 | статья — до 1 млн символов, форма — до 8 МБ, понятные сообщения |

Подробности — в [Статьи: разметка, дерево, версии, поиск](page:Статьи: разметка, дерево, версии, поиск), [База данных](page:База данных) и [Безопасность](page:Безопасность).

## Пропускная способность на чтение

`read-capacity.js`: читатели открывают страницы **без пауз**. Смесь: 60% статей, 10% пространств, 10% главной, 15% поиска, 5% меток.

| Читают одновременно | Запросов/с | Статья p50 / p95 | Поиск p95 | Ошибки |
| --- | --- | --- | --- | --- |
| 1 | 56 | 7 / 12 мс | 117 мс | 0 |
| 5 | 123 | 18 / 34 мс | 277 мс | 0 |
| 10 | 133 | 47 / 83 мс | 338 мс | 0 |
| 20 | 148 | 114 / 165 мс | 375 мс | 0 |
| 40 | 147 | 255 / 362 мс | 555 мс | 0 |
| 80 | 146 | 555 / 693 мс | 852 мс | 0 |

Потолок — **~145 запросов в секунду** (у вошедших пользователей ~118: каждый их запрос ещё и продлевает сессию в базе). Дальше число запросов не растёт, растёт только очередь: задержка увеличивается пропорционально числу читателей, но ошибок нет. Упор — один процесс Node.js (~100% одного ядра) и PostgreSQL, который больше всего нагружает поиск.

## Сколько пользователей работают одновременно

`users.js`: каждый виртуальный пользователь входит под своим логином и ведёт себя как человек — читает статьи, раскрывает дерево, ищет, смотрит историю, ставит в избранное, комментирует; редакторы правят и сохраняют статьи. Между действиями пауза. Пользователи набираются за полторы минуты, затем три минуты работают все сразу. Задержки ниже — именно за это время («удержание»).

| Пользователей | Пауза между действиями | Все запросы p50 / p95 | Статья p95 | Поиск p95 | Ошибки |
| --- | --- | --- | --- | --- | --- |
| 300 | 5–15 с | 13 / 101 мс (весь прогон) | 62 мс | 281 мс | 0 |
| 600 | 5–15 с | 19 / 145 мс (повтор после сна ноутбука: 31 мс / 1,2 с) | 73 мс | 266 мс | 0 |
| 1000 | 5–15 с | 39 / 693 мс (повтор: 272 мс / 11 с) | 0,7 с | 0,8 с | 0 |
| 1500 | 5–15 с | 4,6 / 37 с | 38 с | 37 с | 0,01% |
| **2000** | **30–60 с** | **16 / 116 мс** | **48 мс** | **219 мс** | **0** |

Процессор приложения при 600 активных загружен в среднем на ~65%, при 1000 — на 100% и выше: основной поток плюс пул потоков паролей. Память стабильна: приложение — до 250 МБ, PostgreSQL — ~480 МБ, k6 — до 1 ГБ на 2000 пользователей.

## Наплыв и восстановление

`spike.js`: минуту работают 50 человек, затем за **15 секунд** приходят ещё 950 (все одновременно открыли ссылку из рассылки), две минуты работают 1000, потом снова 50.

| Время | Статья p50 / p95 |
| --- | --- |
| до наплыва | 12 / 16 мс |
| 950 человек входят (~75 секунд) | 4–11 / 5–16 с |
| все вошли, работают 1000 | 0,5–1,4 / 0,8–4 с |
| нагрузка спала до 50 | **сразу** 12 / 17 мс |

Самое дорогое при наплыве — проверка паролей: ~950 × 80 мс работы процессора. Пул потоков распределяет её по ядрам, поэтому портал не «зависает», а отвечает медленнее. Ошибками закончились 0,33% запросов. После наплыва никаких последствий: задержки сразу возвращаются к исходным.

## Длительная нагрузка

600 активных пользователей 10 минут подряд: 47 714 запросов, **43 514 проверок — все пройдены, ошибок нет**. Память не растёт: приложение держится на 190–220 МБ и освобождает её после нагрузки, PostgreSQL — ~480 МБ.

Почти всё время p95 — 20–40 мс. Один раз задержки на 90 секунд выросли до 3–10 секунд, и PostgreSQL в это время загружал 6–7 ядер. Автоочистки таблиц в этот момент не было, планы запросов не параллельные, эпизод не повторился. Вероятнее всего, ноутбук на короткое время приостановил виртуальную машину Docker, а затем база разбирала накопившуюся очередь. На выделенном сервере такого быть не должно; проверить можно тем же сценарием с `HOLD=30m`.

## Загрузка файлов

`uploads.js` — все проверки (856) пройдены.

| Что проверялось | Результат |
| --- | --- |
| Типы файлов | png, jpg, gif, webp, ico, svg, pdf, docx, xlsx, zip, txt, csv, mp4, exe, html, js — **все принимаются** |
| Показ в браузере | **только растровые картинки** (png, jpg, jpeg, gif, webp, avif, bmp, ico); SVG, HTML, JS и всё остальное отдаётся как скачивание (`Content-Disposition: attachment`) |
| Защита | у каждого файла `Content-Security-Policy: sandbox` и `X-Content-Type-Options: nosniff`: загруженный HTML или SVG со скриптом не выполнится |
| Размер | 1 МБ — 37 мс, 10 МБ — 220 мс, 19,9 МБ и **ровно 20 МБ — принимаются**; 20 МБ + 1 байт и 50 МБ — **отказ 413** с понятным сообщением; обрезков отклонённых файлов на диске не остаётся |
| Права | читатель загрузить файл не может (403) |
| 10 редакторов грузят по 5 МБ одновременно | 462 файла за минуту (~38 МБ/с — это темп самого теста), загрузка p50 0,28 с / p95 0,6 с; чтение статей в это время — p95 85 мс, загрузки ему не мешают |

Лимит размера меняется переменной `UPLOAD_MAX_MB`. Файлы хранятся на диске (volume `app-data`), а не в базе, поэтому их общий объём ограничен только диском.

## Размер базы

| Страниц | Размер базы | Статья | Худший поиск | Поиск редкого слова | Метки |
| --- | --- | --- | --- | --- | --- |
| 20 000 | 270 МБ | 7–22 мс | 110 мс | 34 мс | 28 мс |
| 100 000 | 1,36 ГБ | 10–37 мс | 161 мс | 44 мс | 63 мс |

Под нагрузкой на базе в 100 000 страниц:

| | 20 000 страниц | 100 000 страниц |
| --- | --- | --- |
| Потолок чтения (20 читателей без пауз) | 148 запросов/с | 85 запросов/с |
| 600 активных пользователей: все запросы p50 / p95 | 19 / 145 мс | 24 / 375 мс |
| 600 активных: статья p95 / поиск p95 | 73 / 266 мс | 261 / 548 мс |
| Ошибки | 0 | 0 |

Потолок снизился в основном из-за базы данных: с настройками по умолчанию (`shared_buffers` 128 МБ) 1,36 ГБ данных не помещаются в её кэш, а подсчёты на главной и странице меток охватывают в 5 раз больше строк. Для работы людей это пока незаметно: 600 активных пользователей работают так же без ошибок.

Одна страница с историей, поисковым индексом, метками и комментариями занимает в среднем **~13 КБ**, то есть миллион страниц — порядка 13–14 ГБ. Время открытия статьи от размера базы почти не зависит: все выборки идут по индексам. Растут только поиск частого слова (ограничен 1 000 ранжируемых совпадений) и страница меток.

Ограничения самого PostgreSQL на практике недостижимы: таблица — до 32 ТБ, одно поле — до 1 ГБ, размер базы не ограничен. Ограничения портала:

| Что | Предел |
| --- | --- |
| Текст страницы | 1 000 000 символов (~500 страниц А4). Такая статья сохраняется за 0,6 с и открывается за 0,5 с, повторно — за 0,17 с |
| Заголовок | 300 символов |
| Метки | 20 на страницу, по 50 символов |
| Комментарий | 10 000 символов |
| Описание пространства | 20 000 символов |
| Вложение | `UPLOAD_MAX_MB`, по умолчанию 20 МБ |

:::tip Для базы больше ~100 000 страниц
Поднимите `shared_buffers` PostgreSQL до ~25% памяти сервера (по умолчанию 128 МБ) и держите базу на SSD. Редактор страницы в пространстве на 25 000 страниц открывается за ~0,2 с, но его список «Родительская страница» содержит все страницы пространства (2,4 МБ HTML). Для таких пространств стоит сделать список с поиском.
:::

## Как масштабировать дальше

1. **Выделенный сервер.** Уже 4 vCPU и 4–8 ГБ памяти без других нагрузок дадут больше, чем этот ноутбук.
2. **Обратный прокси с gzip** (nginx, Caddy): HTML статьи сжимается с ~30 КБ до ~6 КБ.
3. **Несколько процессов Node.js.** Сейчас портал использует одно ядро для запросов (и ещё до трёх для паролей). Запуск нескольких процессов потребует общего кэша настроек сайта: сейчас каждый процесс хранит его у себя.
4. **Вход через LDAP/SSO** снимает с портала стоимость bcrypt при массовом входе.

## Как повторить

```bash
APP_PORT=18080 ADMIN_PASSWORD=Admin12345 POSTGRES_PASSWORD=testpass AUTH_RATE_LIMIT=100000 \
  docker compose -p wikitest up -d --build
docker compose -p wikitest exec app node src/tools/seed-load.js --yes

k6() { docker run --rm -i --network wikitest_default -v "$PWD/tests/load:/scripts" grafana/k6 run "$@"; }
k6 -e VUS=20 /scripts/read-capacity.js
k6 -e USERS=600 -e RAMP=90s -e HOLD=3m /scripts/users.js
k6 -e USERS=2000 -e RAMP=3m -e THINK_MIN=30 -e THINK_MAX=60 /scripts/users.js
k6 -e BASE_USERS=50 -e SPIKE=1000 /scripts/spike.js
k6 -e UPLOADERS=10 -e UPLOAD_MB=5 /scripts/uploads.js

docker compose -p wikitest down -v   # уборка
```

Не запускайте нагрузку на рабочий портал: сценарии создают страницы, комментарии и файлы.
