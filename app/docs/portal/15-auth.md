## Пользователи и роли (services/users.js)

| Роль | Уровень | Права |
| --- | --- | --- |
| `viewer` — Читатель | 1 | просмотр, поиск, комментарии, избранное |
| `editor` — Редактор | 2 | + пространства, страницы, вложения, откат версий |
| `admin` — Администратор | 3 | + настройки сайта, LDAP, пользователи, удаление пространств |

Глобальная роль — это потолок прав. Где именно редактор может править, а читатель читать, определяют права на пространство: см. [Права доступа к пространствам](page:Права доступа к пространствам).

| Функция | Что делает |
| --- | --- |
| `hasRole(user, role)` | роль пользователя не ниже требуемой |
| `validateUserInput`, `validatePassword` | логин `[a-zA-Z0-9_.-]{3,50}`, email, имя до 100 символов, пароль от 8 символов и не длиннее 72 байт |
| `createUser` | нормализует email, хеширует пароль, нарушение уникальности превращает в понятный `ValidationError` |
| `findUserByLogin(login)` | поиск по логину **или** email без учёта регистра (совпадение логина приоритетнее) |
| `checkLocalPassword(user, password)` | проверка локального пароля; без пользователя или у LDAP-учётки — сравнение с фиктивным хешем |
| `upsertLdapUser(profile)` | создать или обновить учётную запись по данным каталога |
| `initials(name)` | «Иван Петров» → «ИП» для аватара |

**Регистрация** (`routes/auth.js`): разрешена, если включена в настройках **или** в системе ещё нет пользователей. Если администраторов нет, первый зарегистрированный им становится, иначе новичок получает роль из настройки `default_role`.

## Как проверяется вход (services/auth.js)

`authenticateUser(login, password)` возвращает `{ user }` или `{ error, status }`:

```text
есть ЛОКАЛЬНАЯ учётка с таким логином/email?
 ├─ да → только локальный пароль (LDAP не опрашивается!)
 │        └─ LDAP включён и локальный вход запрещён? → пускаем только админов
 └─ нет → LDAP включён?
          ├─ да → ldapAuthenticate → upsertLdapUser
          │        (сервер недоступен → 503 с понятным сообщением)
          └─ нет → «неверный логин или пароль» (+ пустая проверка ради одинакового времени)
```

Затем маршрут проверяет `is_active`, **пересоздаёт сессию** (`regenerateSession`, защита от фиксации сессии), записывает `userId` и `last_login_at`, возвращает пользователя на страницу, с которой его отправили на вход.

:::warning Почему локальная учётка приоритетнее
Иначе сотрудник, у которого в каталоге логин `admin`, вошёл бы в локальную учётную запись администратора сайта.
:::

## LDAP / Active Directory (services/ldap.js)

Схема **search & bind**:

1. `openConnection` — клиент `ldapts` с таймаутами и, при необходимости, STARTTLS;
2. `bindService` — вход служебной учётной записью (Bind DN) или анонимный поиск;
3. `searchUser` — поиск по фильтру: `{{username}}` подставляется **экранированным** по RFC 4515 (`escapeFilterValue`: `\ * ( ) NUL` → `\5c \2a \28 \29 \00`);
4. найдена ровно одна запись → `verifyUserPassword`: bind от её имени **на отдельном соединении**;
5. `buildProfile` — логин, email (если нет — `логин@ldap.invalid`), имя;
6. `resolveRole` — роль по группам.

| Деталь | Почему так |
| --- | --- |
| Пустой пароль отклоняется сразу | bind с пустым паролем — «анонимный вход», многие серверы отвечают на него успехом |
| Больше одной найденной записи — отказ | непонятно, чей это пароль |
| `tlsOptions` передаются в клиент только для `ldaps://` | `ldapts` начинает TLS-рукопожатие уже при наличии `tlsOptions`, и обычный `ldap://` сервер разрывал бы соединение (баг, найденный тестами) |
| `strictDN: false` | Active Directory принимает bind по `user@domain`, хотя это не DN |
| Членство в группе проверяется двумя способами | атрибут `memberOf` (AD, OpenLDAP с overlay) или поиск в группе по `member` / `uniqueMember` / `memberUid` |
| Ошибка поиска группы = «не состоит» | вход не ломается, пользователь получает роль по умолчанию |

**Роль:** если группы администраторов и редакторов не заданы, роль назначается один раз при первом входе (`roleManaged: false`). Если заданы, роль пересчитывается при **каждом** входе: каталог главнее сайта.

`testLdapConnection(login, password)` проходит те же шаги и возвращает журнал `[{ ok, text }]` для кнопки «Проверить» в админке. `describeLdapError` переводит сетевые коды Node (`ECONNREFUSED`, `ENOTFOUND`, ошибки сертификатов) и коды LDAP (32, 49, 50…) в понятные фразы.

## Сессии

- Хранятся в таблице `session` (`connect-pg-simple`), в браузере лежит только подписанный идентификатор в cookie `wiki.sid`.
- **Вход и регистрация** — новая сессия; **выход** — `session.destroy()` и удаление cookie.
- **Смена пароля** и кнопка «Выйти везде» удаляют все остальные сессии пользователя:
  ```sql
  DELETE FROM session WHERE (sess->>'userId')::int = $1 AND sid <> $2
  ```
- **Блокировка и удаление** пользователя администратором сразу удаляют все его сессии.

## Профиль и личные настройки

| Страница | Маршрут | Что можно |
| --- | --- | --- |
| Профиль | `routes/profile.js` | только просмотр: визитка, статистика, правки, избранное |
| Учётная запись | `routes/settings.js` | имя и email (у LDAP-учёток только просмотр: `forbidForLdap`) |
| Безопасность | `routes/settings.js` | пароль (только локальные), выход на других устройствах |
| Оформление | `routes/settings.js` | своя тема (в БД `users.theme`), режим и редактор (в браузере) |

## Управление пользователями (routes/admin.js)

- **Роль, блокировка, пароль** — в карточке `/admin/users/:id`. У LDAP-пользователей поле пароля скрыто, а если роль управляется группами, показано предупреждение.
- **Удаление** требует ввести логин. Контент остаётся с подписью «удалённый пользователь» (`ON DELETE SET NULL`), избранное удаляется.
- **Защиты** (`isLastActiveAdmin`): нельзя понизить, заблокировать или удалить себя и последнего активного администратора.

:::note Удалённый LDAP-пользователь вернётся
При следующем входе через каталог учётная запись будет создана заново. Чтобы закрыть доступ, пользователя лучше **заблокировать** или убрать из каталога. Карточка в админке предупреждает об этом.
:::
