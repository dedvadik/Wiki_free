Права доступа на уровне пространств: кто может читать, кто может править статьи и кто управляет правами. Код — `src/services/permissions.js`, маршруты — `src/routes/spaces.js`, схема — миграция `004_space_permissions.sql`.

[[toc]]

## Модель

Глобальная роль пользователя (`users.role`) задаёт **потолок** его прав, а настройки пространства — **где** эти права действуют.

| Кто | Что может |
| --- | --- |
| **Администратор** | всё во всех пространствах, включая закрытые и удаление |
| **Владелец пространства** (`spaces.owner_id`, изначально создатель) | управлять правами и настройками своего пространства, передавать владение; видит его всегда |
| **Редактор** | править статьи там, где пространство это разрешает |
| **Читатель** | читать всё открытое и закрытые пространства, куда его добавили; комментировать там, где может читать |

Читатель не правит статьи **никогда**, даже если его добавили участником: право редактирования есть только у глобальной роли «Редактор» и выше. Интерфейс не даёт выдать читателю доступ «Редактирование».

## Настройки пространства

| Поле | Значения | Смысл |
| --- | --- | --- |
| `visibility` | `public` — открытое | читать могут все, кому доступен сайт |
| | `restricted` — закрытое | только владелец, участники и администраторы |
| `edit_policy` | `editors` — все редакторы | любой редактор, который **видит** пространство |
| | `members` — только участники | участники с доступом `edit`, владелец и администраторы |
| `owner_id` | пользователь | управляет правами; при удалении пользователя — NULL (тогда управляют только администраторы) |

Участники хранятся в таблице `space_members (space_id, user_id, access, added_by)`, где `access` равно `read` (чтение) или `edit` (чтение и редактирование).

:::info Обратная совместимость
Миграция делает все существующие пространства открытыми с режимом «все редакторы», а владельцем назначает создателя. Поведение сайта после обновления не меняется, пока владелец не изменит настройки.
:::

## Вычисление прав: getSpaceAccess

```javascript
const access = await getSpaceAccess(req.user, space);
// → { canRead, canEdit, canManage, isOwner, member }
```

```text
администратор            → всё можно
иначе:
  isOwner  = space.owner_id === user.id
  member   = уровень из space_members ('read' | 'edit' | null)
  canRead  = visibility = 'public' ИЛИ isOwner ИЛИ member
  canEdit  = canRead И роль ≥ editor И (edit_policy = 'editors' ИЛИ isOwner ИЛИ member = 'edit')
  canManage = isOwner
```

## Проверка в маршрутах: requireSpaceAccess

```javascript
const { space, access } = await loadSpaceWithAccess(req, req.params.key);
requireSpaceAccess(req, access, 'read');   // 'read' | 'edit' | 'manage'
```

- **Гость** без доступа получает `401` со ссылкой «Войти»; адрес запоминается, и после входа пользователь вернётся сюда же (возможно, у него есть доступ).
- **Вошедший** без доступа получает `403` с объяснением, что делать (обратиться к владельцу).

Для страниц есть помощник `loadPageFor(req, id, level)` в `routes/pages.js`: он загружает статью вместе с полями её пространства и сразу проверяет права.

| Действие | Нужный уровень |
| --- | --- |
| просмотр пространства и статьи, история, версии, сравнение, экспорт | `read` |
| комментарий, избранное | `read` + вход |
| создание, правка, удаление, откат статьи; загрузка и удаление вложений | `edit` (и глобальная роль editor+) |
| настройки пространства, права доступа, участники, владелец | `manage` |
| удаление комментария | автор или `manage` |
| удаление пространства | только администратор |

## Фильтрация списков: readableSpacesSql

Закрытое не должно просачиваться ни в поиск, ни в ленты. Поэтому во все выборки, где встречаются страницы или пространства, добавлено SQL-условие:

```javascript
const [isAdmin, userId] = accessParams(req.user);
many(`SELECT … FROM pages p JOIN spaces s ON s.id = p.space_id
       WHERE … AND ${readableSpacesSql('s', '$4', '$5')}`, [..., isAdmin, userId]);
```

```sql
($adm::boolean
  OR s.visibility = 'public'
  OR s.owner_id = $uid::int
  OR EXISTS (SELECT 1 FROM space_members sm WHERE sm.space_id = s.id AND sm.user_id = $uid::int))
```

У гостя `userId = NULL`, а сравнение с `NULL` всегда ложно, поэтому гость видит только открытое. Условие применяется в каталоге пространств, на главной (пространства, недавние изменения, избранное), в поиске, на страницах меток, в профиле. `editableSpacesSql` отбирает пространства, где можно править, для выбора в «+ Создать».

**Вложения** страниц закрытого пространства отдаются только тем, кто может его читать; остальным отвечается `404`, как будто файла нет.

## Страница «Права доступа»

`/spaces/:key/permissions` — владелец и администраторы:

1. **Сводка** словами: кто читает, кто правит, кто управляет.
2. **Режимы:** карточки «Открытое / Закрытое» и «Все редакторы / Только участники».
3. **Владелец:** выпадающий список активных пользователей. Бывший владелец автоматически остаётся участником с доступом «Редактирование», чтобы, передав закрытое пространство, не потерять к нему доступ. Если он не администратор, после передачи его переводит на страницу пространства.
4. **Участники:** смена уровня и удаление. Вариант «Редактирование» у читателей заблокирован.
5. **Добавление** по логину или email с подсказками (`datalist`).

При создании пространства сразу выбирается «Открытое» или «Закрытое»; создатель становится владельцем.

## Интерфейс

- В каталоге, на главной и в боковой панели у закрытых пространств стоит значок замка.
- Кнопки «Новая страница», «Редактировать», «Удалить», «Восстановить» показываются только тем, у кого есть `canEdit`. Сами маршруты всё равно проверяют права повторно.
- Редактор, который видит пространство, но не может в нём править, видит пояснение «В этом пространстве вы можете только читать».
