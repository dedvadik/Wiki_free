# WikiSpace в Kubernetes

Helm-чарт для отказоустойчивого запуска портала с автоматическим масштабированием: копии приложения добавляются при росте нагрузки и убираются при её снижении, узлы кластера — вслед за ними.

## Архитектура: каждый блок — независимый компонент

```text
                    Интернет
                       │
               ┌───────▼────────┐
               │    Ingress     │  TLS, лимит тела под видео, балансировка каждого запроса
               └───────┬────────┘
                       │
   ┌──────────────────────────────────────────┐   HPA: 2…20 копий по загрузке CPU
   │  web  (Deployment)                         │   (или KEDA: по запросам в работе)
   │  ┌──────┐ ┌──────┐ ┌──────┐     ┌──────┐   │   по одной копии на узел / зону
   │  │ pod  │ │ pod  │ │ pod  │ ... │ pod  │   │   PodDisruptionBudget: ≥1 всегда
   │  └──┬───┘ └──┬───┘ └──┬───┘     └──┬───┘   │
   └─────┼────────┼────────┼────────────┼───────┘
         │        │  общий том загрузок (ReadWriteMany)
         │  запись│                     │ чтение (поиск, метки)
   ┌─────▼────────▼───┐          ┌──────▼──────────┐
   │ pooler-rw        │          │ pooler-ro        │   PgBouncer, по копии на узел
   │ (PgBouncer ×2)   │          │ (PgBouncer ×2)   │
   └─────┬────────────┘          └──────┬───────────┘
   ┌─────▼──────────────────────────────▼───────────┐
   │ database — кластер CloudNativePG                │
   │  основной ──репликация──▶ реплика, реплика      │   каждый экземпляр на своём узле,
   │  (запись)                  (чтение)              │   переключение при сбое за 10–30 с
   └─────────────────────────────────────────────────┘
```

| Блок | Ресурс | Отказоустойчивость | Масштабирование |
| --- | --- | --- | --- |
| web | Deployment | ≥2 копии на разных узлах и зонах; PDB; обновление без простоя (maxUnavailable 0); при сбое базы копии не перезапускаются (liveness без обращения к БД) | HPA по CPU (или KEDA по запросам в работе), 2…20 копий |
| pooler-rw / pooler-ro | CloudNativePG Pooler (PgBouncer) | ≥2 копии на разных узлах | `postgresql.pooler.instances` |
| database | CloudNativePG Cluster | основной + реплики на разных узлах, автоматическое переключение, резервные копии в S3 | чтение — на реплики; реплики добавляются через `postgresql.cnpg.instances` |
| storage | PVC ReadWriteMany | как у выбранного хранилища (NFS/CephFS/EFS…) | размер тома |

## Что нужно в кластере

| Компонент | Зачем | Установка |
| --- | --- | --- |
| metrics-server | данные о загрузке CPU для HPA | обычно уже есть; иначе `kubectl apply -f https://github.com/kubernetes-sigs/metrics-server/releases/latest/download/components.yaml` |
| Ingress-контроллер | вход снаружи | ingress-nginx или встроенный в облако |
| Оператор CloudNativePG | кластер PostgreSQL (`postgresql.mode: cnpg`) | `helm repo add cnpg https://cloudnative-pg.github.io/charts && helm install cnpg cnpg/cloudnative-pg -n cnpg-system --create-namespace` |
| Хранилище ReadWriteMany | общий том загрузок для всех копий | NFS (nfs-subdir-external-provisioner), CephFS, Longhorn, AWS EFS, Azure Files, файловое хранилище Yandex Cloud |
| Автоскейлер узлов | добавлять и убирать **узлы** вслед за копиями | Cluster Autoscaler / Karpenter; в управляемых кластерах — включить автомасштабирование группы узлов |
| (по желанию) cert-manager | сертификаты TLS | `ingress.tls.clusterIssuer` |
| (по желанию) Prometheus + KEDA | масштабирование по метрикам приложения | `keda.enabled`, `serviceMonitor.enabled` |

## Установка

```bash
# 1. Образ (мультиплатформенный) — в свой реестр
docker buildx bake --set '*.tags=registry.example.com/wikispace:1.0.0' --push

# 2. Портал
helm install wiki ./kubernetes/helm/wikispace -n wiki --create-namespace \
  --set image.repository=registry.example.com/wikispace --set image.tag=1.0.0 \
  --set ingress.host=wiki.example.com

# или с готовым набором настроек для боевого кластера:
helm install wiki ./kubernetes/helm/wikispace -n wiki --create-namespace \
  -f kubernetes/examples/values-production.yaml

# 3. Пароль администратора
kubectl -n wiki get secret wiki-wikispace-app -o jsonpath='{.data.ADMIN_PASSWORD}' | base64 -d; echo
```

Тестовый кластер из одного узла (k3s, kind, minikube) — без оператора и RWX-хранилища: `-f kubernetes/examples/values-small.yaml`.

**Kubernetes от Docker Desktop с провайдером kind (несколько узлов)** — отдельная пошаговая инструкция с готовыми настройками: [kubernetes/kind/README.md](kind/README.md).

Обновление: `helm upgrade wiki ./kubernetes/helm/wikispace -n wiki -f …`. Копии обновляются по очереди без простоя. Миграции базы применяет init-контейнер новой копии до того, как она начнёт принимать запросы. Секрет сессий и пароль сохраняются, пользователей не разлогинивает.

## Как работает автомасштабирование

```text
нагрузка ↑ → CPU копий > 70% requests → HPA: до ×2 копий за 15 с
           → новым копиям не хватает места → Pending → автоскейлер добавляет узел
нагрузка ↓ → CPU низкий 5 минут подряд → HPA: −1 копия в минуту (плавно)
           → узел опустел → автоскейлер удаляет узел → мощность высвобождается
```

Все параметры — в `values.yaml` (`web.autoscaling`), значения по умолчанию выбраны по нагрузочному тестированию:

| Параметр | По умолчанию | Почему |
| --- | --- | --- |
| `minReplicas` | 2 | сайт переживает падение узла и обновление |
| `maxReplicas` | 20 | потолок; поднимайте вместе с `pooler.defaultPoolSize` и `max_connections` |
| `requests.cpu` | 500m | одна копия насыщается на ~1 ядре (~145 запросов/с) |
| `targetCPUUtilizationPercentage` | 70 | 0,35 ядра ≈ 50 запросов/с на копию — запас до насыщения, низкие задержки |
| рост | ×2 или +4 копии за 15 с, без ожидания | всплеск нельзя пережидать |
| снижение | после 5 минут низкой нагрузки, ≤1 копии или 10% в минуту | не «дёргаться» на коротких провалах |
| по памяти | выключено | Node.js не спешит отдавать память после пика — HPA не смог бы уменьшить число копий |

KEDA (`keda.enabled: true`) масштабирует ещё и по числу запросов в работе (`wikispace_http_requests_in_flight`): реагирует на всплеск раньше, чем вырастет загрузка CPU. `vpa.enabled: true` включает VerticalPodAutoscaler в режиме рекомендаций: он подскажет `requests` по реальному потреблению.

## Отказоустойчивость

- **Падение копии или узла.** Балансировщик перестаёт слать запросы на копию, как только её `/healthz` не отвечает. Kubernetes поднимает замену; PDB не даёт плановым работам выселить все копии сразу.
- **Остановка копии** (обновление, уменьшение числа копий). `SIGTERM` → `/healthz` отвечает 503 → копия выходит из балансировки, ещё `shutdownDelaySeconds` принимает запоздавшие запросы и дорабатывает начатые. Пользователи ошибок не видят.
- **Сбой основного PostgreSQL.** CloudNativePG за 10–30 с делает основным самую свежую реплику и перенастраивает сервисы; приложение переподключается само. `livenessProbe` не проверяет базу, поэтому копии web при этом не перезапускаются.
- **Несколько копий — одна база.** Миграции, создание администратора и импорт документации выполняются под advisory-блокировками PostgreSQL: сколько бы копий ни стартовало одновременно, работу сделает одна. Настройки, изменённые в админке на одной копии, остальные подхватывают за `settingsSyncSeconds` (5 с).

## Что изменилось в приложении для работы в нескольких копиях

Всё включается переменными окружения. В обычном `docker compose` поведение прежнее.

| Переменная | Что делает |
| --- | --- |
| `RUN_MIGRATIONS=false` | не готовить базу при старте: это делает init-контейнер `node src/tools/prepare.js` напрямую с PostgreSQL (мимо PgBouncer) |
| `DATABASE_READ_URL` | поиск и страница меток читают с реплик |
| `SETTINGS_SYNC_SECONDS` | как часто перечитывать настройки сайта из базы |
| `SHUTDOWN_DELAY_SECONDS`, `SHUTDOWN_TIMEOUT_SECONDS` | двухэтапная корректная остановка |
| `METRICS_PORT` | метрики Prometheus на отдельном внутреннем порту |

Кроме того:

- добавлена проверка `/livez` (жив ли процесс, без базы);
- версии статики и `/theme.css` — хеш содержимого, одинаковый у всех копий;
- keep-alive 65 с (дольше, чем у nginx), чтобы не было случайных 502;
- безопасная генерация секрета сессий при одновременном старте.

## Как проверялось

Кластер k3s v1.34 (один узел в Docker), metrics-server, traefik, оператор CloudNativePG v1.30.1.

- **Статическая проверка.** `helm lint` проходит на всех наборах настроек. Отрендеренные манифесты прошли строгую проверку kubeconform по схемам Kubernetes 1.30 и CRD (CloudNativePG, Prometheus Operator): 27 из 27 ресурсов корректны.
- **Подготовка базы двумя копиями одновременно.** Одна выполнила миграции, создала администратора и опубликовала документацию. Вторая дождалась блокировки и ничего не повторила («без изменений 20»).
- **Взаимозаменяемость копий** — 12 из 12 проверок:
  - вход на копии A, работа на копии B;
  - файл, загруженный через A, копия B отдаёт байт в байт;
  - версии статики и `/theme.css` совпадают;
  - изменённое в админке название сайта копия B показала через 3 с;
  - `/livez`, `/healthz` и метрики отвечают.
- **Нагрузка и масштабирование** (k6 через Ingress, 30 одновременных пользователей без пауз):

| Время | Что происходило | Копий web |
| --- | --- | --- |
| 0–35 с | нагрузка растёт, CPU копий до 441% от requests | 2 |
| 41 с | HPA: сразу до максимума (рост ×2 за 15 с) | 2 → 6 |
| 52 с | новые копии прошли init-контейнер и готовы (~11 с) | 6 |
| 151 с | удаление копии под нагрузкой: замена готова за ~20 с, ошибок нет | 6 |
| 202 с | обновление всех копий по очереди под нагрузкой | 6 |
| 258 с | нагрузка снята | 6 |
| +60 с | HPA плавно убирает копии (в тесте — окно 60 с; по умолчанию 5 минут и 1 копия в минуту) | 6 → 4 → 2 |

- **Обновление без ошибок.** Первый прогон дал 17 ошибок 502 из 51 781 запроса: прокси повторно использовал keep-alive соединение с останавливающейся копией. Исправлено: при остановке копия отвечает с `Connection: close`. После исправления два полных обновления всех шести копий под нагрузкой — **0 ошибок из 38 995 запросов** (210 запросов/с).
- **Кластер PostgreSQL (CloudNativePG):** 3 экземпляра — основной и 2 реплики.
  - Поиск действительно выполняется на реплике (соединение приложения видно на реплике).
  - **Сбой основного сервера под непрерывной нагрузкой:** pod основного удалён принудительно, как при падении узла. Приложение снова читает и пишет примерно через 20 секунд. Оператор назначил основным реплику, а пересозданный экземпляр вернулся репликой; кластер снова 3/3 через 51 секунду.
  - Запросы за это окно: не прошли 9 из 276 чтений, 9 из 276 поисков, 3 из 69 записей.
  - Копии web не перезапускались: 0 рестартов, liveness не зависит от базы.
- **Пулеры PgBouncer.** CloudNativePG принял ресурсы Pooler чарта и создал их pod'ы. Запустить их на тестовом стенде не удалось: образ `ghcr.io/cloudnative-pg/pgbouncer` не скачался за время теста, как и образ PostgreSQL 18 по умолчанию. Поэтому кластер проверялся с `imageName: postgres:17-alpine`, `extraSpec: { postgresUID: 70, postgresGID: 70 }` и `pooler.enabled: false`. На кластере с нормальным доступом к ghcr.io используйте значения по умолчанию.

## Ограничения

- Лимит попыток входа (`AUTH_RATE_LIMIT`) считается в каждой копии отдельно: при N копиях фактический лимит — до N×.
- Для нескольких узлов нужен том ReadWriteMany. Хранение файлов в S3 (без общего тома) пока не поддерживается.
- Кастомизация через `custom.files` удобна для нескольких файлов; для большого набора соберите свой образ (`FROM wikispace` + `COPY custom /app/custom`).
